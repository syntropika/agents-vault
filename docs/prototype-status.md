## Security findings

The broker must be outside the agent's authority. A process name, PID check, loopback listener, or VM around only the child command does not protect secrets if another agent-controlled process can reach the vault or private administration. A raw MCP client synthesized a positive form response. The adapter receives no administration token or vault passphrase. An authenticated operator may explicitly enroll its trusted MCP harness session for bounded action decisions, using a memory-only session proof. App-only visibility is a harness trust assumption, not human authentication. Local console and private terminal decisions remain available. This closes that direct form-response route in the Linux synthetic guest. However, after approval, any client with the agent UID and request ID can call `Execute` first and obtain the host proxy capability. A holder can send arbitrary requests to the allowed host within the quota, and a client with the action ID can call `FinishHostProxy`. These are high-severity limits of shared-UID host execution. Keychain or another storage API does not distinguish those clients. The protected release claim remains disabled until the operator entry point and every supported agent route pass joined adversarial tests on both installed platforms.

An exact-host proxy cannot infer provider-side permissions. The test proxy verifies CONNECT host, TLS name, and HTTP host, but request semantics and provider response filtering belong to an integration policy. Do not use a production credential to prove the current fixture.

Use the local CLI for configuration and explicitly trusted direct delivery. Use synthetic credentials and the fixture CLI for proxy and approval tests.
